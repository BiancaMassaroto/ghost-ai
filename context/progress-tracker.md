## Architecture Decisions

- Route protection lives in `proxy.ts` at the project root, not `middleware.ts` — Next.js 16 renamed the file convention (`middleware` → `proxy`); the API and semantics are otherwise unchanged.
- Clerk `appearance` is themed once, centrally, in `lib/clerk-appearance.ts` (`{ theme: dark, variables: {...} }` using this Clerk version's `theme` key, not the older `baseTheme` prop) and passed to `ClerkProvider` in the root layout, rather than repeated per-component — all Clerk UI (`SignIn`, `SignUp`, `UserButton`) inherits it automatically.
- Project data flows server → client one-way: `app/editor/page.tsx` and `app/editor/[roomId]/page.tsx` (renamed from `[projectId]` in `08-editor-workspace-shell.md`) fetch via `lib/get-projects.ts` and pass props down; `hooks/use-project-actions.ts` never holds its own copy of the project list, it triggers `router.refresh()`/`router.push()` after a mutation and lets the server component re-fetch. This replaces the earlier two-hook mock-data split (`useMockProjects` + `useProjectDialogs`) noted in prior sessions — superseded by `07-wire-editor-home.md`.
- A project's database `id` (Prisma `cuid()`) is the single identifier used everywhere, including as the future Liveblocks room ID — there is no separate stored "room ID" field. The create dialog's room-ID preview is cosmetic (client-generated slug+suffix) and does not become the real ID; see `07-wire-editor-home.md` notes above for why.
- `proxy.ts`'s middleware-level `auth.protect()` now applies only to page routes, not `/api`/`/trpc`. API routes enforce auth per-route instead (`lib/api-auth.ts`'s `requireUserId()`), because Clerk's `auth.protect()` doesn't return `401` for unauthenticated non-document (API) requests — it redirects or 404s. Any new `app/api/*` route must call `requireUserId()` itself; it will not get auth protection from `proxy.ts`.
- The page-background color token is exposed to Tailwind as `bg-canvas`, not `bg-base` (its CSS variable is still `--bg-base`). Registering it as `--color-base` collided with Tailwind's own font-size scale key `base` (`text-base` = 1rem); a color theme value wins that collision, so every `text-base` in the app (the create/rename project dialog inputs, `DialogTitle`, `Card` title, `Textarea`, the auth layout headline) was silently rendered as `color: var(--bg-base)` — near-black text on a near-black card — instead of getting a font size. See the reserved-name note in `context/ui-context.md`.
- Collaborators are identified by email only (`ProjectCollaborator.email`), never by Clerk user ID — there's still no invite flow that resolves an email to a Clerk account at invite time, only at *display* time (`lib/clerk-users.ts`, `09-share-dialog.md`). This means inviting an email with no Clerk account is allowed (it just displays as email-only in the Share dialog and never gains project access via Clerk auth, since `checkProjectAccess` matches on the signed-in user's own email). Clerk's `getUserList({ emailAddress: [...] })` filter is an exact match (distinct from `UserCountParams`'s documented partial-match behavior for the same field name) — verified via its `.d.ts` before relying on it.
- Liveblocks room permissions use ID-token auth (`liveblocks.identifyUser`), whose access is static per-room (set once via `getOrCreateRoom`'s `defaultAccesses`), not per-request. Every room is created with `defaultAccesses: ["room:write"]` (permissive), because the real gate is upstream: `/api/liveblocks-auth` only ever issues a token for a room after `checkProjectAccess` passes, so nobody can obtain a valid token for a room they don't have project access to in the first place. Don't read the room's own permissiveness as the access control — it isn't; `lib/project-access.ts`'s `checkProjectAccess` is.
- The canvas's Liveblocks Storage schema is one field, `flow: LiveblocksFlow<CanvasNode, CanvasEdge>` (`liveblocks.config.ts`), fully owned by `@liveblocks/react-flow`'s `useLiveblocksFlow` — no other code reads or writes `storage.flow` directly. `types/canvas.ts` is the single source for the node/edge shape (`CanvasNodeData`, the `"canvasNode"`/`"canvasEdge"` type tags, `NODE_COLORS`/`NODE_SHAPES`), so it's shared by both the live canvas and (once built) template import/AI generation, per `architecture-context.md`'s "canvas schema must remain consistent between user-created content and imported templates" invariant.
- Superseded by `24-ai-presence-state.md`, below: `LiveblocksProvider`/`RoomProvider` now wrap `CanvasRoom` *and* `AiSidebar` together, mounted in `components/editor/editor-shell.tsx` rather than inside `canvas-room.tsx`. They still don't live any higher (e.g. root layout) — `RoomProvider` still needs a concrete `id` (the active project's ID), which still only exists once a room is open — and `CanvasRoom` still owns the room-specific `ErrorBoundary`/`ClientSideSuspense` around `Canvas`, just not the Provider itself anymore. This moved because a second Liveblocks consumer (`AiArchitectTab`'s `useIsAiThinking`/`useLatestAiStatus`) needed the same room's context without re-mounting it — exactly the scenario this decision used to flag as the reason to revisit. `AiSidebar` is now only ever rendered inside the `activeProject` branch in `editor-shell.tsx` (previously always mounted, just visually collapsed) so its Liveblocks hooks always have a real `RoomProvider` ancestor — any future Liveblocks-consuming component added to that sidebar can rely on this without its own Provider check.
- Canvas nodes/edges are created and mutated by calling `useLiveblocksFlow`'s own `onNodesChange`/`onEdgesChange` with a real React Flow change object (e.g. `{ type: "add", item }` for a new node, per `12-shape-panel.md`'s drop handler in `canvas.tsx`) — never by writing to `storage.flow`'s `LiveMap`s directly. This keeps the existing invariant ("`useLiveblocksFlow` is the single owner of `storage.flow`," from `11-base-canvas.md`'s notes above) intact for every future canvas-mutating feature (node editing, AI-generated nodes, template import), not just user drag-drop.
- The project sidebar and AI sidebar push/reflow the canvas panel — each is a flex sibling of the canvas whose own width animates between `0` and its open width, so opening/closing one resizes the canvas next to it. This supersedes `02-editor.md`'s original "floats above the canvas and never pushes layout" decision (explicit user instruction); that spec file is left as-is (historical record of what its own unit shipped), but any new workspace-chrome work should follow this reflow behavior, not the older overlay one, per `ui-context.md`'s current Layout Patterns section.
- A `canvasNode` renderer reaches node-mutating actions (e.g. `updateNodeLabel`) via `CanvasNodeActionsContext` (`components/editor/canvas/canvas-node-context.tsx`), provided by `CanvasFlow` in `canvas.tsx` — never via `useReactFlow()`'s own `updateNodeData`/`setNodes`. Those write to React Flow's internal store, which is bypassed entirely while `<ReactFlow>` runs controlled (`nodes={nodes}` from `useLiveblocksFlow`), so a change made that way would never reach Liveblocks Storage and would just be overwritten by the next external update. Every node mutation triggered from inside a node renderer must be dispatched as a real `NodeChange` through `onNodesChange` (surfaced to the renderer via this context), same as node creation already does — future per-node actions (color/shape editing, etc.) should add to `CanvasNodeActions` rather than introducing a second way to mutate a node. `16-edge-behavior.md` established the identical pattern for edges — `CanvasEdgeActionsContext` (`canvas-edge-context.tsx`), `EdgeReplaceChange` through `onEdgesChange` — for the same reason: an edge renderer only receives `EdgeProps`, not `onEdgesChange`, and `<ReactFlow>` runs controlled for `edges` too.
- New edges default to the `"canvasEdge"` type (and the app's stroke color/arrowhead) via a module-scope `defaultEdgeOptions` object passed to `<ReactFlow>` (`canvas.tsx`), rather than by setting `type` explicitly wherever an edge gets created. React Flow fills in any unset `Edge` field from `defaultEdgeOptions` at the point an edge is added — this is what makes the existing `onConnect` wiring (unchanged since `11-base-canvas.md`) produce `CanvasEdge`-rendered connections with no changes needed at the connection-creation call site itself.
- Canvas undo/redo (`17-canvas-ergonomics.md`) uses Liveblocks' own room history (`useUndo`/`useRedo`/`useCanUndo`/`useCanRedo` from `@liveblocks/react`) with no app-level history code — it requires no extra wiring precisely because of the invariant above: every canvas mutation already flows through `onNodesChange`/`onEdgesChange`, and Liveblocks records history for any Storage write made that way, regardless of which UI action triggered it. Any future canvas mutation that follows the established `*ReplaceChange`-through-`on*Change` pattern is automatically undo/redo-able for free; a mutation that bypassed it (writing to `storage.flow` directly, or through `useReactFlow()`'s uncontrolled-mode helpers) would silently fall outside undo/redo history too.

- A workspace-chrome trigger (navbar button, sidebar toggle, etc.) that needs to drive a canvas-scoped action threads its state down as plain props through `CanvasRoom` → `Canvas` → `CanvasFlow`, rather than the action itself moving up to `EditorShell` — `EditorShell` owns *open/closed*, `CanvasFlow` owns *what actually happens*, since it's the only place with `nodes`/`edges`/`onNodesChange`/`onEdgesChange`/`reactFlowInstance`. Established by `18-starter-template.md`'s starter templates modal (`isTemplatesModalOpen`/`onTemplatesModalOpenChange`); any future feature in the same shape (an AI-generate-onto-canvas trigger, etc.) should follow the same split rather than inventing a second way to reach into the canvas from outside its tree.
- Presence UI (`19-presence-avatars-cursor.md`) lives entirely inside the canvas subtree — `PresenceAvatars`/`LiveCursors` are only ever mounted by `CanvasFlow` (`canvas.tsx`), never by `EditorShell`/`EditorNavbar` — so it's structurally impossible for it to leak into the editor home screen or the shared navbar; no route/view flag was needed to scope it. A cursor's presence value (`Presence.cursor`) is stored in *flow* coordinates (via `screenToFlowPosition`, the same conversion the shape-drop handler already used), not raw screen coordinates, and rendered through `@xyflow/react`'s `<ViewportPortal>` rather than as a plain `<ReactFlow>` child — `ViewportPortal` renders into `.react-flow__viewport` itself (the pannable/zoomable layer), while a plain child (like `<ShapePanel>`) renders as its *sibling* (per `13-node-shape.md`'s note on where `<ReactFlow>` children land) and would stay fixed to the screen regardless of pan/zoom. Any future canvas overlay that should move/scale with node positions (not screen-fixed chrome like a toolbar) should use `<ViewportPortal>` the same way.
- Canvas persistence (`21-canvas-autosave.md`) is a snapshot of Liveblocks Storage, not a second source of truth for it — `storage.flow` (synced live via `useLiveblocksFlow`) remains the only thing the canvas actually renders from; `Project.canvasJsonPath`/Vercel Blob only exist to *seed* a room that comes up empty and to survive across rooms being torn down. Loading a saved snapshot writes it into `storage.flow` via the same `onNodesChange`/`onEdgesChange` path every other canvas mutation uses (never a second, parallel state source), and only when the room is genuinely empty — an active collaborative session is never overwritten by a stale blob. `checkProjectAccess` (owner-or-collaborator), not `requireProjectOwner`, gates both the save and load routes, matching the fact that canvas editing itself is already collaborative.
- The reverse of the "workspace-chrome trigger threads down through `CanvasRoom` → `Canvas` → `CanvasFlow`" pattern above also uses a plain prop through the same three components, just carrying a callback instead of a value: `21-canvas-autosave.md`'s `onSaveStatusChange` lets `CanvasFlow` (the only place with the live `nodes`/`edges` autosave needs) report status up to `EditorShell`, which is where the value actually needs to be read (the navbar's save indicator) since `EditorNavbar` has no independent access to Liveblocks state — `RoomProvider` is mounted locally in `CanvasRoom`, not at the root. Any future canvas-internal state that a chrome component outside the canvas subtree needs to display should follow this same up-threading, rather than lifting `RoomProvider` itself or giving `EditorNavbar` its own Liveblocks hooks.

- The installed `@trigger.dev/sdk` is `3.3.17` — on this version, `task`/`logger`/`tasks`/`auth`/`defineConfig` must be imported from the `@trigger.dev/sdk/v3` subpath, not the bare `@trigger.dev/sdk` root export (confirmed empirically against `node_modules`' own `.d.ts` files, per `AGENTS.md`, since `tsc` disagreed with what both the bare-package imports already in the repo and the bundled `trigger-setup`/`trigger-authoring-chat-agent` skills' example code do). Every `trigger/*.ts` file and `trigger.config.ts` follows this; any new Trigger.dev code should too, until/unless the SDK is deliberately upgraded to a version where the skills' guidance applies as written.

- A background job (a Trigger.dev task, not a browser client) that needs to write into a room's `storage.flow` does so over Liveblocks' JSON Patch REST endpoint (`lib/liveblocks.ts`'s `patchRoomStorage`), not the Node SDK's `mutateStorage`, and not by hand-building `LiveObject`/`LiveMap` structures — established by `23-design-agent-logic.md` per Liveblocks' own "Enabling Agentic Workflows" guide (a backend agent with no live connection is the documented use case for this endpoint). `mutateStorage` requires knowing the exact Live-structure shape `@liveblocks/react-flow` expects for a node/edge (which fields the library keeps as plain values vs. converts to nested `LiveObject`s), which isn't documented; JSON Patch instead writes plain JSON matching `types/canvas.ts`'s `CanvasNode`/`CanvasEdge` shape and lets Liveblocks convert it, the same way `initializeStorageDocument`/a client's `onNodesChange` already do. Any future backend (non-browser) canvas mutation should follow this same pattern, not introduce a third way to write `storage.flow`.
- A backend agent that needs to "be present" in a room without a live WebSocket connection uses `liveblocks.setPresence(roomId, { userId, data, userInfo, ttl })` (ephemeral, auto-expiring) — not a fake client connection, not a new presence mechanism. It flows through the exact same `useOthers()`/`Presence` path a real connected user's presence does, so it already renders in every existing presence-driven UI (`PresenceAvatars`, `LiveCursors`) with no changes to those components. A one-off status announcement (not ongoing presence) publishes to the room's `ai-status-feed` Liveblocks feed instead (`lib/liveblocks.ts`'s `publishAiStatus`, `types/tasks.ts`'s `AI_STATUS_FEED_ID`/`aiStatusFeedMessageSchema`) — established by `24-ai-presence-state.md`, superseding `23-design-agent-logic.md`'s original `liveblocks.broadcastEvent`/`RoomEvent` approach (kept in `liveblocks.config.ts` only as an unused, documented-dead type now) once a real Feeds primitive turned out to exist in the installed `@liveblocks/node`/`@liveblocks/react`, undocumented on liveblocks.io as of this session but present in both packages' own `.d.ts` files. Any future backend-originated status announcement (e.g. `generate-spec`'s eventual progress) should publish to the same feed with the same schema — it's deliberately generic, not design-generation-specific — rather than inventing a parallel status channel or a second feed.

- Liveblocks feeds are one-per-purpose, not one-per-app: `25-sidebar-chat-feed.md` added a second feed, `ai-chat` (room-scoped collaborative chat), deliberately kept separate from `ai-status-feed` (AI generation progress) rather than folding chat messages into the status feed with an extra discriminator field. Since Liveblocks types `FeedMessageData` globally rather than per-feed, this makes it a union (`AiStatusFeedMessage | AiChatFeedMessage`, in `liveblocks.config.ts`) — every feed's own hook (`use-ai-status-feed.ts`, `use-ai-chat-feed.ts`) is responsible for re-validating a message against its own specific Zod schema before trusting `.data`, since the union alone doesn't say which feed a given message came from. Any future distinct real-time message stream (e.g. a future spec-generation log) should follow this same pattern — a new feed ID + schema in `types/tasks.ts`, added to the `FeedMessageData` union — rather than overloading an existing feed with a mixed-purpose payload shape.
- `ensureAiStatusFeed`/`ensureAiChatFeed` (`lib/liveblocks.ts`) share one private `ensureFeed(roomId, feedId)` helper for the "create or reuse" check-then-create logic, added when the second feed made the duplication concrete (`25-sidebar-chat-feed.md`). Any future room-scoped feed should add its own `ensureXFeed` wrapper around this same helper, called from `/api/liveblocks-auth` at room-join time, rather than re-implementing the check-then-create logic per feed.
- Not every Liveblocks feed needs a server-side `publish*` helper: `ai-status-feed` does (`publishAiStatus`, called from backend tasks with no live connection), but `ai-chat` doesn't — its messages are always sent by a connected client via `useCreateFeedMessage` (`hooks/use-ai-chat-feed.ts`), so there's nothing for a server-side publisher to do. Add one only when a message on a given feed can originate from backend code, not preemptively for every feed.

- Starting a design generation run from the client is two requests, not one, despite `26-design-agent-frontend.md`'s spec describing a single `POST /api/ai/design` call returning `{runId, publicToken}`: `22-design-agent-api.md` already shipped `POST /api/ai/design` returning only `{runId}`, with the run-scoped public token issued separately by `POST /api/ai/design/token` (`{runId}` in, `{token}` out, ownership-checked against the `TaskRun` the first call recorded). `hooks/use-design-run.ts` calls both in sequence rather than the backend being changed to match the frontend spec's wording — `26-design-agent-frontend.md` itself scoped out backend/Trigger.dev changes, and the two-request shape is also the more defensible one: a client never receives a token for a run it didn't just create and isn't verified to own. Any future caller that needs to start a run and subscribe to it should follow `useDesignRun`'s two-call pattern, not assume the spec's literal single-response shape.
- `ai-chat` messages authored by the app itself (not a connected participant) are just a normal feed message with `role: "assistant"` and `sender: "Ghost AI"` — not a separate mechanism, and not something a server-side task publishes directly (unlike `ai-status-feed`'s `publishAiStatus`). `26-design-agent-frontend.md`'s final-result/error messages are pushed by the *client* that started the run, via the same `useCreateFeedMessage`-backed `sendMessage` every user message already goes through (`hooks/use-ai-chat-feed.ts`, now taking an optional `role` argument) — once a run settles for the client that's subscribed to it via `useRealtimeRun`. Any future AI-authored chat message should follow this same client-side-push pattern unless a use case actually requires a backend task to author a chat message with nobody subscribed client-side to trigger it.
