## Architecture Decisions

- Route protection lives in `proxy.ts` at the project root, not `middleware.ts` — Next.js 16 renamed the file convention (`middleware` → `proxy`); the API and semantics are otherwise unchanged.
- Clerk `appearance` is themed once, centrally, in `lib/clerk-appearance.ts` (`{ theme: dark, variables: {...} }` using this Clerk version's `theme` key, not the older `baseTheme` prop) and passed to `ClerkProvider` in the root layout, rather than repeated per-component — all Clerk UI (`SignIn`, `SignUp`, `UserButton`) inherits it automatically.
- Project data flows server → client one-way: `app/editor/page.tsx` and `app/editor/[roomId]/page.tsx` (renamed from `[projectId]` in `08-editor-workspace-shell.md`) fetch via `lib/get-projects.ts` and pass props down; `hooks/use-project-actions.ts` never holds its own copy of the project list, it triggers `router.refresh()`/`router.push()` after a mutation and lets the server component re-fetch. This replaces the earlier two-hook mock-data split (`useMockProjects` + `useProjectDialogs`) noted in prior sessions — superseded by `07-wire-editor-home.md`.
- A project's database `id` (Prisma `cuid()`) is the single identifier used everywhere, including as the future Liveblocks room ID — there is no separate stored "room ID" field. The create dialog's room-ID preview is cosmetic (client-generated slug+suffix) and does not become the real ID; see `07-wire-editor-home.md` notes above for why.
- `proxy.ts`'s middleware-level `auth.protect()` now applies only to page routes, not `/api`/`/trpc`. API routes enforce auth per-route instead (`lib/api-auth.ts`'s `requireUserId()`), because Clerk's `auth.protect()` doesn't return `401` for unauthenticated non-document (API) requests — it redirects or 404s. Any new `app/api/*` route must call `requireUserId()` itself; it will not get auth protection from `proxy.ts`.
- The page-background color token is exposed to Tailwind as `bg-canvas`, not `bg-base` (its CSS variable is still `--bg-base`). Registering it as `--color-base` collided with Tailwind's own font-size scale key `base` (`text-base` = 1rem); a color theme value wins that collision, so every `text-base` in the app (the create/rename project dialog inputs, `DialogTitle`, `Card` title, `Textarea`, the auth layout headline) was silently rendered as `color: var(--bg-base)` — near-black text on a near-black card — instead of getting a font size. See the reserved-name note in `context/ui-context.md`.
- Collaborators are identified by email only (`ProjectCollaborator.email`), never by Clerk user ID — there's still no invite flow that resolves an email to a Clerk account at invite time, only at *display* time (`lib/clerk-users.ts`, `09-share-dialog.md`). This means inviting an email with no Clerk account is allowed (it just displays as email-only in the Share dialog and never gains project access via Clerk auth, since `checkProjectAccess` matches on the signed-in user's own email). Clerk's `getUserList({ emailAddress: [...] })` filter is an exact match (distinct from `UserCountParams`'s documented partial-match behavior for the same field name) — verified via its `.d.ts` before relying on it.
- Liveblocks room permissions use ID-token auth (`liveblocks.identifyUser`), whose access is static per-room (set once via `getOrCreateRoom`'s `defaultAccesses`), not per-request. Every room is created with `defaultAccesses: ["room:write"]` (permissive), because the real gate is upstream: `/api/liveblocks-auth` only ever issues a token for a room after `checkProjectAccess` passes, so nobody can obtain a valid token for a room they don't have project access to in the first place. Don't read the room's own permissiveness as the access control — it isn't; `lib/project-access.ts`'s `checkProjectAccess` is.
- The canvas's Liveblocks Storage schema is one field, `flow: LiveblocksFlow<CanvasNode, CanvasEdge>` (`liveblocks.config.ts`), fully owned by `@liveblocks/react-flow`'s `useLiveblocksFlow` — no other code reads or writes `storage.flow` directly. `types/canvas.ts` is the single source for the node/edge shape (`CanvasNodeData`, the `"canvasNode"`/`"canvasEdge"` type tags, `NODE_COLORS`/`NODE_SHAPES`), so it's shared by both the live canvas and (once built) template import/AI generation, per `architecture-context.md`'s "canvas schema must remain consistent between user-created content and imported templates" invariant.
- `LiveblocksProvider`/`RoomProvider` are mounted locally inside `components/editor/canvas/canvas-room.tsx`, not higher up the tree (e.g. root layout) — the canvas is currently the only Liveblocks consumer (the AI sidebar is still a static placeholder), and `RoomProvider` needs a concrete `id` (the active project's ID), which only exists once a room is actually open at `/editor/[roomId]`. Revisit this placement if a second Liveblocks consumer (e.g. the AI sidebar) needs the same room's context without re-mounting it.
- Canvas nodes/edges are created and mutated by calling `useLiveblocksFlow`'s own `onNodesChange`/`onEdgesChange` with a real React Flow change object (e.g. `{ type: "add", item }` for a new node, per `12-shape-panel.md`'s drop handler in `canvas.tsx`) — never by writing to `storage.flow`'s `LiveMap`s directly. This keeps the existing invariant ("`useLiveblocksFlow` is the single owner of `storage.flow`," from `11-base-canvas.md`'s notes above) intact for every future canvas-mutating feature (node editing, AI-generated nodes, template import), not just user drag-drop.
- The project sidebar and AI sidebar push/reflow the canvas panel — each is a flex sibling of the canvas whose own width animates between `0` and its open width, so opening/closing one resizes the canvas next to it. This supersedes `02-editor.md`'s original "floats above the canvas and never pushes layout" decision (explicit user instruction); that spec file is left as-is (historical record of what its own unit shipped), but any new workspace-chrome work should follow this reflow behavior, not the older overlay one, per `ui-context.md`'s current Layout Patterns section.
